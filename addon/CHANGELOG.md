## [2026.08.25-4ed686ae] - 2026-08-25 18:45

### 🐛 Bug Fixes

- Fix(iot): decide IoT support from Govee's metadata, not a model list

Two independent notions of "can use AWS IoT" existed, and the wrong one
decided routing:

  Device::iot_api_supported()      a hardcoded SKU list in quirks.rs
  IotClient::is_device_compatible  does the device have an MQTT topic

The second is the truth -- it is what the client itself checks before
publishing. The first had drifted: of the eleven models on this account
only H6072 appeared in quirks.rs, so ten of them were routed to the
Platform API and its daily request quota. They were not incapable; the
debug log shows an H601B, absent from the list, returning a complete
status packet over IoT.

A topic is now necessary and sufficient, except that a quirk may still
veto it -- four models are listed as unsupported because IoT misbehaves
for them despite having one. The field became Option<bool> so that "no
opinion" is distinguishable from "explicitly no", which a plain bool
defaulting to false could not express.

The polling path was already safe: poll_iot_api applies the topic test
itself and falls through to the Platform API when it cannot publish.
What changes is which transport is tried first.

### 🚀 Features

- Feat(iot): read a device back after an AWS IoT command

poll_after_control skipped IoT devices outright, on the assumption that
a device volunteers its new state over that channel. It does for the
whole-device attributes -- but not for per-segment colours, which are
only ever reported when asked, and an IoT command is never acknowledged
at all: the broker accepts the publish and says nothing more. A command
that quietly did nothing would leave Home Assistant showing a state the
light never reached.

It now requests an IoT status after the same delay the Platform API path
already used. That costs no Platform quota -- it rides a connection we
already hold -- and it refreshes segment entities as a side effect.

The delay itself is configurable now (--poll-after-control, default 5,
so unchanged), because how long a device needs before it reports
honestly is a per-installation question.

LAN and Bluetooth stay exempt for the reasons they always were: a
Bluetooth session reads back the attributes it changed, and the LAN path
verifies its own writes. The LAN check moved above the IoT one so that a
device with both is still skipped rather than newly polled.

### 🚀 Features

- Feat(poll): make the poll interval configurable, per transport

The 15 minute figure was a constant in serve.rs with no way to change
it. It is now four settings, because the four transports do not cost the
same thing: a LAN query is a UDP packet on your own network, an AWS IoT
request rides a connection already open, a Platform API call spends part
of a daily quota, and a Bluetooth poll occupies a proxy connection slot.
One number would have forced those against each other.

  --poll-interval           900  shared default for iot/platform/ble
  --poll-interval-lan        30  local and free
  --poll-interval-iot       900  where per-segment colour comes from
  --poll-interval-platform  900  the one with a quota behind it
  --poll-interval-ble       900  costs a proxy slot while it runs

Defaults reproduce the previous behaviour exactly. Zero is rejected
rather than interpreted -- on the Platform API it would empty the quota
in minutes.

Three things worth knowing about the implementation:

- The loop tick follows the shortest configured interval, clamped to
  5-30s. Without that a short interval would silently round up to the
  fixed 30s tick.
- The LAN query ran on every tick, ungated. It is gated on
  last_lan_device_status_update now, which answers "how old is the LAN
  picture" rather than "when did we last ask".
- The diagnostic Status sensor used the same constant to decide what
  counts as missing. It follows the longest configured interval now,
  otherwise raising one interval to save quota would have marked healthy
  devices as gone.

Every add-on option now has a name and a description. The Bluetooth and
transport-order ones never had any and showed as raw keys in the add-on
configuration UI.

Also drops two stale claims that Bluetooth is the preferred transport,
in docs/CONFIG.md; D2b made it last by default.

The Platform API reports segment state as an empty string, which is what §15
recorded. Turning on debug logging for the IoT module shows the device sending
it anyway, as raw BLE frames that iot.rs discards for want of a codec.

AA A5 <page> carries three groups of brightness plus RGB, so three segments per
frame. Captured from an eight-segment H6072 in a known state; all checksums

spontaneously, so segment state would refresh on the poll interval rather than
live. And what is still unconfirmed: the mapping from frame slot to segment
entity.

- Docs(segments): confirm the AA A5 frame slot to segment entity mapping

A four-colour calibration on the H6072 settles the open question from
section 17: segment_00N addresses frame slot N-1, counted from the
bottom, and eight entities cover exactly eight visible bands.

The earlier apparent mismatch was a magenta/cyan naming mix-up in the
spoken report, not a gap in the frames.

### 🚀 Features

- Feat(segments): read per-segment colour from the AWS IoT channel

The Platform API answers segmentedColorRgb with an empty string, so
segment entities had no state at all. The device volunteers it over the
undocumented channel instead, as aa a5 frames carrying three segments
per page, and iot.rs was dropping them.

Three parts:

- ble.rs gains a NotifySegmentColors codec, with the three frames
  captured from a real H6072 as regression tests.
- iot.rs retries an undecodable frame under GENERIC_LIGHT. The light
  codecs are not registered under any SKU, so ordinary colour frames
  were coming back as Generic too.
- Device keeps the pages in a segment_colors map and the segment light
  entities publish real colour.

Segments stay optimistic: whether every segmented SKU emits these frames
is unknown, and a device that never reports would otherwise lose the
feedback it has today. The per-segment brightness byte is decoded but
not published, because its scale is not understood.

## [2026.08.25-d2418f9b] - 2026-08-25 14:57

### 🚀 Features

- Feat(segments): send segments sharing a value in one request, and allow off

Govee's segmentedColorRgb and segmentedBrightness capabilities take an array of
segment indices, but Home Assistant models each segment as its own light
entity, so a scene fans out into one request per segment. Fifteen for a garden
tree, each one a cloud round trip.

service/segments.rs collects the commands that arrive together, groups them by
the value asked for, and issues one request per distinct value. Measured on an
eight-segment floor lamp: four segments in two colours now cost two requests
instead of four.

Switching a segment off previously did nothing. Upstream had ruled out
brightness 0 for good reasons, since some devices have no 0 and the rest power
the whole device up, which would flick a whole area back on while turning it
off. Setting the colour to black has neither problem.

Worth recording from the same session: Govee reports per-segment state as an
empty string, so reading it back is not possible and the optimistic entities
are the only honest option rather than a shortcut upstream took.

## [2026.08.25-216df5ae] - 2026-08-25 13:06

### 🐛 Bug Fixes

- Fix(ble): fall back instead of queueing, and allow correcting an address

Three findings from a hallway routine run while proxies were being moved.

Waiting for a free session slot queued the command behind radio work of
unknown length while a perfectly good cloud transport sat idle. The wait is now
bounded at 500ms, after which BLE declines and the router moves on. That is
what falling back when the proxies are busy has to mean in practice.

A job that burns its whole 30s budget is not an ordinary failure: it already
cost the caller half a minute and says the device is not answering. Requiring
two more before setting the device aside spent another minute proving what was
already known, so a timeout now opens the circuit breaker at once.

The address is now logged with each session, and can be corrected per device.
That is needed because Govee's metadata is not always right: one H601B reported
an address one higher than the one derived from its device id. That address
advertised at -68 dBm with free connection slots and still refused every
connection, while the derived form worked on a sibling device.


## [2026.08.25-f1cb4a84] - 2026-08-25 12:31

### ⚡ Performance

- Perf(ble): take the read-back out of the critical path

A motion-triggered hallway routine driving two downlights took 6-10 seconds.
Every session carried three frames and three verification queries, and at 200ms
between operations that is a second of deliberate waiting plus three notify
round trips before the caller learns the light is on.

Verification now runs after the waiters are notified and the concurrency permit
is released. The connection is still open, so the read-back costs no reconnect;
it simply no longer delays the command that prompted it, nor the next device
waiting for a permit.

Home Assistant still learns the new state from the read-back rather than
optimistically, so what it sees is unchanged. What changes is when the next
device may start.


### 📚 Documentation

- Docs: the fork is developed independently from now on

Nothing goes back upstream and rebases onto wez/govee2mqtt are not planned.
Earlier work was deliberately additive to keep that door open; that constraint
is lifted, so invasive edits are fair game where they make the code better.


## [2026.08.25-05374164] - 2026-08-25 11:18

### 🚀 Features

- Feat: make the transport order configurable, and put BLE last by default

The order was only settable through a CLI flag, which an add-on user cannot
reach. It now also reads GOVEE_TRANSPORT_ORDER and has an add-on option.

The default changes from Bluetooth-first to Bluetooth-last. The fork's premise
was Bluetooth as the preferred transport; a day of live use revised that, and
the owner's reasoning is sound: stability and speed come first, and Bluetooth
does not yet earn a place ahead of paths that are proven. LAN deserves to lead
regardless, being both faster than Bluetooth and the only transport that
verifies its own work.

other transport, so every other one declines and Bluetooth serves it anyway.
What changes is that cloud-capable devices keep using the cloud until Bluetooth
has earned promotion, which is now one setting away.

Scenes no longer list Bluetooth at all: there is no verified scene encoding, so
offering it only added a transport that would decline.

## [2026.08.25-a87dc1a5] - 2026-08-25 11:06

### 🐛 Bug Fixes

- Fix(ble): brightness and colour must switch the light on themselves

Home Assistant sends 'turn on at 60%' as brightness alone, and upstream's
command handler leans on that: when brightness or colour is present it sends no
power command at all, because the cloud and LAN APIs power a device on as a
side effect of setting either one.

The BLE frames have no such side effect. 33 04 <percent> sets the brightness and
nothing more, so the light stayed dark and quietly remembered how bright it
would have been. Observed on real hardware: a turn_on carrying brightness and
colour temperature produced two sessions, neither of which switched anything on.

An explicit power state still wins, so switching off while also setting
brightness does not helpfully switch the light back on.


### 🚀 Features

- Feat(ble): carry a light command's attributes in one session

Coalescing did not work in the path that matters. upstream's
mqtt_light_command awaits each attribute in turn, so the scheduler's 150ms
window never saw two at once: a turn_on with brightness and colour temperature
produced two sessions of one frame each, which real hardware duly showed.

Transport gains a batch path. The default runs the operations in order, which
is what the cloud and LAN APIs need anyway; BLE overrides it to merge them into
a single radio session. A transport that declines before doing anything lets
the router move on, while one that declines after something has taken effect is
an error rather than a fallback, since retrying elsewhere would apply the
earlier operations twice.

Also makes the session concurrency configurable. One at a time is the safe
default, but it serialises a scene across several lights at 1.5-4s each. The
companion integration has a matching worker-pool setting that has to be raised
alongside it.


## [2026.08.25-95238916] - 2026-08-25 10:35

### 🐛 Bug Fixes

- Fix(ble): one connect attempt, and put the signal level in the error

Measured against real hardware: bleak-retry-connector ignores the timeout
passed to establish_connection and enforces its own 20s per attempt. A second
attempt cannot fit a 30s budget, so it starts, gets cut off part way, and

a debug log. A connect timeout looks identical whether the device is barely in
range or refusing outright, and that is where someone will be looking: the
device that prompted this reported -100 dBm, which is the noise floor.

### 🚀 Features

- Feat(ble): let individual devices be kept off Bluetooth

BLE could already be turned off globally. This adds the finer control: a
comma separated exclusion list where each entry matches a device id, SKU or
name, so one entry can exclude a single light or a whole model.

Matching mirrors what resolve_device already accepts (id, name, computed name,
MQTT topic id) plus the SKU, so anything the user can name a device by works.

An entry matching no known device is reported at startup. It would otherwise
fail silently: the device would keep using Bluetooth and the user would be left
wondering why the exclusion had no effect.

  "Error: Please specify the mqtt broker"

that happen when using the default implicit broker credentials
as described in the docs.

Some users report that this issue occurs on startup of haos
and that restarting or deferring startup of govee2mqtt will
resolve this.

Other users report that explicitly configuring credentials
and the mqtt endpoint resolves things for them.  I suspect
this latter case is actually a separate issue, but that it
manifests in a very similar way.

Looking at zigbee2mqtt I can see that it enables the hassio api option
in its addon configuration; it's really unclear from the addon
development guide docs when this is needed because for me and most other
users, the addon works fine without it.  I've set it to true in this
commit as a speculative measure.

The other thing that I saw when reviewing zigbee2mqtt was this issue:
https://github.com/home-assistant/supervisor/issues/3884 where it
appears as though there is some kind of startup race condition between
addons, despite the addon configuration stating that mqtt is required
for us to start.  Their resolution was to use the bashio library to
assert that a basic config option was present.  We can't do literally
that, but we can check that either the mqtt broker is up or that the
mqtt_host option is set, and bail out early if both conditions are not
met.

Hopefully that will persuades HAOS's supervisor watchdog to try us again
in a little bit, and hopefully make the mqtt details available to us.

### 🚀 Features

- Feat(sensor): add `state_class=measurement` to temp./humid.
- Feat(ble): complete the light command and notification codecs

Adds the frames a BLE light transport needs beyond the power command that was
already registered: brightness, RGB, colour temperature, and decoders for the
three status notifications.

Expectations in the tests are frames captured from real devices, transcribed
from the reverse-engineering repositories.

Notable decisions:

- Kelvin rejects zero while OptionalKelvin does not. A white RGB frame and a
  colour temperature frame share their first six bytes, so the Kelvin field is
  the only thing that tells them apart while decoding. In a notification zero
  is meaningful: it says the device is showing an RGB colour rather than white.
- Notification decoders are hand-written rather than generated by the packet!
  macro, because the macro requires every trailing byte to be zero. That holds
  for frames we generate, but rejecting a device's status update over a stray
  padding byte would be a poor trade. They verify the checksum instead.
- Queries are free functions rather than codecs, since a query and its matching
  notification share a header and would decode ambiguously.
- The RGB companion value the official app appends to colour temperature frames
  is omitted. Its captured values do not match the approximation the Python
  reference code uses, so we cannot reproduce it faithfully, and both reference
  implementations leave it out without ill effect.

Brightness is encoded as a plain byte, 0x00-0x64. The Python reference
implementations render the percentage as a decimal string and then parse it as
hex, turning 20% into 0x13; that is documented in the code so it does not get
reintroduced as a "fix".

- Feat(component): add the govee_ble_executor Home Assistant integration

The add-on cannot reach Bluetooth itself: it runs in a container with no
Bluetooth stack, and an ESPHome proxy accepts exactly one advertisement
subscriber, so it cannot speak to the proxies alongside Home Assistant without
the two stealing the subscription from each other. This integration closes the
gap by executing GATT operations inside Home Assistant, exchanging jobs with the
add-on over MQTT.

It is deliberately generic and knows nothing about Govee. The add-on sends
"connect to this MAC, write these bytes, optionally hand back the notification",
so all protocol knowledge stays in ble.rs and this side stays small.

A request describes a whole session rather than a single write, so a burst of
commands costs one connection instead of several.

Throttling lives here because Home Assistant has none of its own:
establish_connection does not wait for a free connection slot, it fails and
retries with backoff, so parallel jobs really do produce parallel connects. A
fixed worker pool, one worker by default, is the whole mechanism, which keeps us
out of the regime where habluetooth's path scorer starts penalising us and
leaves the household's other Bluetooth devices alone.

Errors are typed with an optional retry hint so the add-on's scheduler can tell
"retry shortly" from "switch transport"; out_of_slots and not_found carry Home
Assistant's reachability diagnostics, which name the per-proxy slot usage.

Sessions follow the led-ble pattern: connect lock, operation lock, idle
disconnect timer, no auto-reconnect. The BLEDevice is resolved fresh before
every connect, since bleak-retry-connector's ble_device_callback has been inert
for some time and a stale device object simply fails to connect.

The wire protocol is specified in component/README.md and is the contract the
Rust side implements next.

- Feat(ble): add the BLE transport and its scheduler

Wires the executor integration into the add-on as a first-class transport,
preferred over LAN and cloud for the light operations it understands.

Scheduling is the substance here. Home Assistant provides no BLE queue, and an
ESP32 proxy has around three connection slots, so a burst of commands that turns
into a burst of connections is exactly how Bluetooth control becomes unreliable.
Three mechanisms address that: commands for one device inside a 150ms window
merge into a single session, one session runs at a time, and a device that fails
three times in a row is set aside for five minutes so the router falls through to
the cloud.

Device addresses are derived rather than guessed. deviceSettings.address is
preferred, with the Govee device id as a fallback; both were verified against the
account data in test-data, where the id turns out to be the address with two
bytes prepended.

Details worth noting:

- Switching a device off suppresses every other frame in the same session.
- Brightness 0 is sent as 1, since zero means "off" on the wire and a brightness
  command that silently switches the light off would be a surprise.
- Colour and colour temperature displace each other while coalescing; they are
  the same opcode with different arguments, so keeping both would send two
  conflicting frames back to back.
- The concurrency permit is held across the whole MQTT exchange rather than
  released on publish, otherwise the next session would start while this one
  still owns a connection slot.
- BleTransport is the only transport that falls through on error: a failing radio
  link should hand over to the cloud, not surface as a failed command. An open
  circuit breaker or an offline executor reports NotSupported instead, so routing
  past it stays quiet.
- A dropped MQTT connection marks the executor offline immediately; the retained
  status message cannot be trusted once updates stop arriving.

Also makes the transport order configurable via --transport-order, which is what
the abstraction was for, and adds the add-on options and documentation.

Query ops are deliberately left unused for now. The wire format models them and
the executor implements them, but reflecting BLE state in Home Assistant needs a
fourth source in Device::device_state(), which belongs with re-enabling BLE-only
devices.

- Feat(ble): read device state over Bluetooth and surface BLE-only lights

Bluetooth becomes a source of truth rather than just a way to send commands.

Device gains ble_device_status as a fourth candidate in device_state(),
alongside LAN, HTTP and IoT. It is merged rather than replaced: each
notification covers a single attribute, so the setter takes a closure over the
running picture instead of a whole status.

After a command session the scheduler reads back only the attributes it changed.
Verifying everything would triple the length of a session that set one
attribute, and since writes are unacknowledged this is what catches a frame the
device dropped. Switching a device off reads back power alone, there being
nothing else worth asking about.

Notifications are matched by content rather than by position, so a device that
answers out of order, or answers only some of the queries, still tells us
something useful.

Bluetooth-only lights whose address is known are no longer hidden from Home
Assistant. That is deliberately not conditioned on the executor being online:
entities appearing and disappearing with it would be worse than one that is
briefly unavailable. Their state is refreshed on the usual poll interval;
last_polled is recorded before the attempt so an unreachable device is retried
on that interval rather than on every tick of the poll loop.

Devices that also have a LAN or cloud presence keep their existing polling,
since their Bluetooth writes are already verified in-session.
